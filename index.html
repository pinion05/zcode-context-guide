ZCode의 컨텍스트를
읽어내는 법

독자는 이미 안다 — 컨텍스트 윈도우, prompt caching, sliding-window 요약, 툴 결과 절단, 세션 영속을. 이 글은 그 지식 위에 ZCode(지에이전트 데스크톱 에이전트)가 그 문제들을 어떻게 특유의 방식으로 재실현했는지를 bundle(out/host·out/scheduler)과 런타임(db.sqlite·model-io)을 교차검증해 보여준다. 각 단위는 “익숙한 패턴 → ZCode의 Δ”로 전개한다.

READER PROFILE

에이전트 루프와 컨텍스트 방법론에 해박하지만 ZCode는 처음. 따라서 기초 개념은 건너뛰고, ZCode가 그 개념을 어떤 구체적 메커니즘으로, 왜 그렇게, 실현했는지를 벤치마크 시스템과 대비하며 설명한다.

SOURCE @zcode/desktop v3.7.5/ BACKEND GLM-5.2 · api.z.ai (Anthropic 호환)/ VERIFY bundle ↔ db.sqlite ↔ rollout
00

ZCode in 60 seconds이 시스템은 무엇이고, 컨텍스트 매니지먼트는 어디에 사는가

ZCode는 지에이전트(Z.AI)의 데스크톱 코딩 에이전트다. Electron 앱이며, 백본 모델은 자사 GLM-5.2를 api.z.ai/api/anthropic(Anthropic Messages 호환 엔드포인트)를 통해 쓴다 — 즉 Anthropic 스펙을 말하지만 Claude가 아닌 독특한 위치다. 이 사실이 아래 전체에 영향을 준다(prompt caching·tool_use·thinking 스펙을 그대로 쓰되 동작은 GLM).

두 프로세스는 JSON-RPC “ZCode Protocol”(trusted channel, session/send·session/compact·automation/create 등 라우트)로 통신한다. 핵심은 컨텍스트 매니지먼트가 UI도, 스케줄러도 아닌 host 프로세스(에이전트 커널)에 있다는 점 — 이후 모든 메커니즘은 이 커널 안에서 일어난다.

01

메탈모델다섯 겹의 방어벽 — 그리고 익숙한 패턴과의 매핑

ZCode는 컨텍스트를 하나의 큰 “줄이기” 문제로 보지 않는다. 대신 목적이 다른 다섯 개의 독립된 밸브로 취급한다. 한 밸브가 느슨하면 다음 밸브가 보완하는 식. 당신이 아는 패턴들이 어디에 대응하는지 먼저 매핑하자.

THE CORE INSIGHT
런타임 관측에서 ZCode는 요약 모델콜을 드물게 발화한다. 대신 session_target 기반 구조적 연속(continuation)이 주 압축 수단이고, 요약(compaction) 경로는 존재하되 1M 윈도우 안에 드는 세션에선 dormant. 두 축은 “압축해 넣기 vs 새 페이지로 넘기기”라는 서로 다른 전략의 보완 관계다.

7-소스 컨텍스트 예산rS enum — 예산 산정을 진단 도구로

FAMILIAR → ZCODE
토큰 예산 = input_tokens 하나. “컨텍스트가 찼다”는 사실만 안다.
→
컨텍스트를 7개 소스로 분해해 각 chars를 센다. “무엇이 찼는가”를 안다.
왜? — 병목이 메시지인지 스키마인지 스킬인지 알아야 조치(툴 끄기·스킴 다이어트)가 가능하다.

rS = n.enum([

  "tool_prompt", "system_tool_schemas",

]) // 각 값마다 chars 카운트 → compaction.terminal에 노출

03

시스템 프롬프트 계층화 · 캐시캐시 단위를 쪼개 히트율을 극대화한다

FAMILIAR → ZCODE
하나의 큰 시스템 프롬프트 문자열을 통째로 cache_control.
→
4-layer 고정 블록을 각각 독립 캐시 블록으로 분리. 어디가 바뀌어도 다른 층은 히트 유지.
왜? — Anthropic 캐시는 “접두어 일치” 기반이라, 뒤쪽 한 글자 바뀌면 그 뒤는 캐시 미스. 층을 나누면 변경된 층만 미스.
// request.body.system — Anthropic cached text blocks
[
  { type:"text", text:"You are ZCode, an interactive coding agent",
    cache_control:{type:"ephemeral"} },            // L1 정체성 (거의 안 변함)
  { type:"text", text:"You are an agent for ZCode CLI…" },   // L2 페르소나
  { type:"text", text:"Notes: - Agent threads have cwd reset…" }, // L3 운영 메모
  { type:"text", text:"…<env>Working directory: …</env>" }   // L4 환경 (cwd 등)
]

동적 인젝션

  • <system-reminder> user-role 블록 — currentDate 같은 경량 상태를 흘린다.
  • Skills 블록 — 활성 스킬 name+설명만 (~15.8KB). 본문은 progressive disclosure로 호출 시점에만 주입.
  • Tool 스키마 — 활성 툴의 input_schema가 별도 소스(system/mcp_tool_schemas)로 분리 추적.
OBSERVED PAYOFF
한 턴의 usage: input 4172 + cacheRead 3072 = 7244 토큰 중 42%가 캐시 적중. GLM 백엔드에서도 Anthropic 호환 캐시가 작동한다는 증거이며, 캐시 단위를 쪼갠 설계가 비용을 가른다.
04

컨텍스트 윈도잉messageOffset / Count — 활성 창의 명시적 추적

FAMILIAR → ZCODE
슬라이딩 윈도우: 최근 N개 메시지를 기계적으로 유지. “모델이 지금 뭘 보는가”는 불투명.
→
messageOffset(시작)·messageCount(개수)로 활성 창을 명시. compaction 이력이 offset 점프로 반영.
왜? — 윈도우 경계를 compaction·continuation과 정합시켜 “잘린 게 아니라 요약으로 교체됐다”를 모델에게 일관되게 보여주기 위해.
필드의미 · 관측
messageOffset활성 창 시작. compaction 후 firstKeptEntryId 이후로 점프.
0 = 압축 없이 전체 히스토리
messageCount이번 요청 메시지 수. 턴이 쌓이며 증가.
관측: 한 턴에 7 → 51 (14회 모델콜)
messagesKind"full"(완전 스냅샷) / "delta"(증분, 메타 희소) — 트레이스 밀도 조절
maxOutputTokens맥락 기반 출력 캡 (예: 99072)
output_config.effort추론 강도 ≡ thinkingLevel ≡ variant (예: "max") — 세 표현이 같은 값
05

Compaction 엔진요약은 후처리가 아니라 1급 턴이다

FAMILIAR → ZCODE
/compact 같은 수동 요약, 또는 단일 임계값 자동 요약. 부수적인 정리 작업.
→
compaction은 1급 메시지 파트(type:"compaction")이자 1급 턴 종류(activeTurnKind:"compact"). 자체 상태머신·재시도·5 트리거.
왜? — 요약을 “터진 뒤 비상 조치”가 아니라 예방적으로 스케줄되는 일급 연산으로 격상시켜, 실패/부분/재시도를 정석적으로 다루기 위해.

파이프라인

5종 트리거 중 하나 판정
→
02 / PREPARE
컷 포인트
firstKeptEntryId 산정, 분할 턴 처리, 직전 요약 참조
→

요약 생성

}

5 트리거의 의미 — 왜 5개인가

trigger언제 · 왜 별도인가
manual사용자 명시 /compact. 사용자 주도.
autocontextWindow − reserve 임계 사전 도달. 터지기 전에 예방.
partial터진 경계를 안 쓰는 범위에서 부분 요약. 무결성 보존.
reactive이미 overflow 발생 후 반응式. 1회 재시도와 쌍.
session_memory세션 복원/핸드오프 시 기억 정비. 세션 단위 요약 동기화.
FAILURE MAPPING
원인을 정규식 분류: /abort|cancel|interrupt|stop/i.test(reason) ? "interrupted" : "failed" — 사용자 중단과 진짜 오류를 구분해 기록. 재시도 정책이 이 값에 의존한다.

타임라인엔 type:"context_compaction", display:"separator"로 나타나며 operationId·boundaryId·summaryMessageId로 원본과 요약을 연결한다. 이전 메시지는 브라우징 가능하지만 모델 컨텍스트엔 빠진다 — 사용자 경험과 모델 관점을 분리하는 깔끔한 설계.

06

Target-Budget 연속continuation — ZCode만의 차별적 설계

FAMILIAR → ZCODE
한 작업이 윈도우를 초과하면 → 강제 요약으로 구겨 넣거나, 잘라내거나, 실패.
→
session_target 예산 도달 시 새 run을 열고 summary_title을 끌고 “계속”. 요약이 아니라 페이지 전환.
왜? — 대규모 리팩터/장기 작업에선 요약이 정보를 잃는다. 예산을 리셋하고 깨끗한 컨텍스트에서 이어가는 쪽이 손실이 적다.
tokens_used = 0~71% 사용token_budget
active — 예산 소진 중 budget_limited — 도달, continuation paused — 사용자 일시정지 
// db.sqlite · session_target 테이블 (runtime)
session_target(
  session_id, target_id,              -- target_mspe0zzs_…
  objective,
  status CHECK('active','paused','budget_limited','complete'),
  token_budget, tokens_used, time_used_seconds,
  summary_title,                       -- goal_summary_title_generation이 채움
  active_input_id, active_run_started_at, active_run_last_seen_at
)

전문가 프레이밍: compaction이 “과거를 압축해 현재 창에 넣기”라면, continuation은 “예산을 리셋하고 새 창에서 이어가기”다. 이 둘은 정반대 전략이며 ZCode는 둘 다 갖는다 — 요약이 적합한 짧은 맥락엔 compaction, 연속이 적합한 긴 작업엔 continuation. target.continuation.started 이벤트로 새 run이 열리고 summary_title이 맥락을 이어받는다.

07

툴 출력 예산화budgetStrategy — 거대 stdout의 우아한 처리

FAMILIAR → ZCODE
툴 결과를 maxTokens에서 절단. 잘린 부분은 영영 소실.
→
artifact: 전체를 파일로 offload하고 모델엔 참조(persisted-output)만 반환. truncate: 절단 + 공지. 원본은 보존.
왜? — 빌드 로그/테스트 출력은 “지금 다 안 봐도 된다”지만 “나중에 다시 봐야 할 수도 있다”. 참조 패턴이 이 둘을 모두 만족.

artifact

출력 전체를 파일로 쓰고, 모델에는 참조만. 원본은 디스크에 보존되어 이후 탐색 가능.

// part.metadata.serialization
{
  budgetStrategy: "artifact",
  originalBytes: 1803,
  returnedBytes: 120,
  artifactPath: "…/sess_…/call_…-stdout.log"
}

truncate

maxBytes에서 절단하고 잘렸음을 알리는 꼬리를 붙인다. 빠르고 단순.

…
[output truncated: 50211 ->
       8192 bytes]

모델은 <persisted-output originalBytes="…">…path…</persisted-output>를 보고, 필요하면 Read/Bash로 부분적으로 재방문한다. 이것이 ZCode가 거대 출력을 다루는 방식 — 컨텍스트는 보호하되 정보는 버리지 않는다.

08

입력 큐 모델session_input — 손실 없는 스티어링

FAMILIAR → ZCODE
긴 턴 중 입력: 큐에 쌓아 턴 끝에 처리 OR 즉시 인터럽트. 둘 중 하나.
→
3-way delivery + 생애주기. startNow(인터럽트) · guide(인플라이트, 기본) · queue(다음 턴). admitted→promoted.
왜? — “지금 바꾸고 싶다” vs “지금 하던 거 끝내고 봐라” vs “중간에 참고만 해라”를 한 매커니즘으로 표현.
delivery동작비고
startNow진행 중 턴을 인터럽트하고 즉시 주입긴급 정정·중단
guide진행 중 턴에 인플라이트 가이드로 흘림zcodeInteractionBehavior:"guide" — 기본값
queue현재 턴 종료 후 다음 턴에 주입순차 큐잉
 
// 입력 생애주기
admitted  ─▶  promoted   (promoted_message_id로 실제 메시지 생성)
   │
   └─▶ cancelled | discarded | failed   (status_reason 사유 기록)

5분째 턴을 도는 중에도 “잠깐, 방향 바꿀게”가 입력되면 — 그 말이 사라지지 않고 의미있는 시점에 합류한다. 이것이 ZCode가 “반응형 에이전트”이기 위한 기반.

09

재시도 · 백오프컨텍스트 문제와 실패 복구의 결합

컨텍스트 관리는 실패 복구와 맞닿아 있다. 모델 요청은 model.request.status로 단계 추적되고, 일시 오류는 지수 백오프. 핵심 결합: 길이 초과 실패는 reactive compaction과 쌍으로 처리된다 — 실패 원인이 “컨텍스트가 크서”면, 줄이고 같은 턴을 재시도. 

// model.request.status phase
[ "model_request_started", "model_request_completed", "model_request_failed",
  "model_retry_scheduled", "model_stream_stalled" ]

{ attempt, maxAttempts, delayMs, nextAttempt, idleMs, timeoutMs, retryable, statusCode }
  • retryable 참일 때만 model_retry_scheduled 백오프 (delayMs/nextAttempt).
  • stream_stalled — 스트리밍 정지 별도 감지/복구.
  • 길이 초과 시 1회 reactive compaction 후 동일 턴 재시도 — “포기”가 아니라 “줄이고 다시”.
10

영속 스키마db.sqlite — event-sourced 세션

ZCode 세션은 이벤트 소싱에 가깝다. message → part 이중 구조에, 의미있는 사건(모델콜·터ン·툴·compaction·입력)이 각각 전용 테이블에 기록되어 재생/분석 가능하다.

콘텐츠 트리

  • session — 루트 (parent_id로 포크/서브에이전트 트리)
  • message — role별 컨테이너, data JSON에 모델/모드/토큰
  • part — text/tool/reasoning 블록, sequence 자동번호

부가 로그

  • session_entry — 타입별 append-log (compaction·라벨·모드변경)
  • session_target — 목표 예산/연속
  • session_input — 입력 큐(delivery/status)
  • turn_usage / model_usage / tool_usage
tool_usage × PERMISSION LEAK
tool_usage는 read_only·destructive·side_effect_scope·approval_status 칼럼을 갖는다 — 권한 게이팅이 영속 계층까지 스며들어 있고, plan 모드의 “읽기전용 강제”가 이 분류에 의존한다. 컨텍스트 매니지먼트와 권한이 같은 스키마에서 만나는 지점.
11

전체 파이프라인한 턴이 지나는 길 — 모든 메커니즘의 합주

① 빌드
system_prompt + skills + tool_schemas + messages를 7-소스로 조립. 각 층 cache_control:ephemeral.
② 윈도잉
messageOffset/Count로 활성 창 결정. compaction 이력 반영.
③ 게이팅
권한 모드(plan/build/edit/yolo/auto)로 툴 허용/차단. tool_usage에 분류 기록.
④ 호출
Anthropic Messages 스트리밍(GLM). 실패 시 model.request.status 백오프, overflow 시 reactive compaction.
⑤ 툴 실행
출력은 budgetStrategy(artifact/truncate)로 절단/offload → part로 부착.
⑥ 턴 종료
turn_end. session_target.tokens_used 갱신. 예산 도달 시 continuation.
⑦ 압축
임계 도달 시 compaction.terminal(5 트리거). 요약 엔트리로 교체.
⑧ 영속
message/part/session_entry/session_input/usage 테이블에 이벤트 기록. 재생 가능.
ONE-LINER
ZCode의 컨텍스트 매니지먼트는 “층위가 다른 다섯 개의 밸브”다 — 예산 진단(7-소스) → 요약(compaction) → 작업 단위 리셋(target/continuation) → 출력 절단(budget) → 캐시/윈도잉. 각 밸브가 독립적으로 열리고 닫히며, 한 층의 부족함을 다음 층이 보완한다. 익숙한 패턴들이 진단 가능하고, 일급이고, 재생 가능한 형태로 재실현된 곳.
